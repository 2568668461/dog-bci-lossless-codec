# 压缩管线移植领航者 ZYNQ 开发板规划

日期：2026-09-07 ｜ 项目：犬类嗅觉 BCI 128ch Intan 无线化 ｜ 依据：`0906_真实Intan数据压缩测试报告.md` 附一~附七实测结论 + 正点原子《领航者 ZYNQ 之 FPGA 开发指南》第 4 章

---

## 0. 结论（要点前置）

1. **"移植"的真实含义**：现有算法代码（drice、T1 树、drice_nl）全部是 **Python 参考模型，没有一行 RTL**。移植 = 以 Python 为黄金模型（golden model）做 **RTL 实现 + 板级验证**，验收标准是**输出位流与 Python 逐位一致**。
2. **移植对象选定 T1+drice 无损管线**（附七结论：1.949×，FPGA 亲和，每通道 1 个减法器）。FLAC 立体声（1.99×）是 hub 层软件方案，不在植入端 PL 内实现；JPEG-LS NEAR 近无损（2.58×）作为二期可选项。
3. **板卡够用且余量大**：XC7Z020（85K LC / 4.9Mb BRAM）承载 128ch 压缩管线绰绰有余；若只有 7010（28K LC / 2.1Mb）也够——压缩核心估计 <5K LC。推荐 7020，为后续 spike 检出/Wi-Fi 模块留余量。
4. **板上没有 Wi-Fi 6，用千兆以太网（YT8521/YT8531）模拟无线链路**——千兆 > Wi-Fi 6 实际吞吐（数十 Mbps），链路层验证不受影响；真实 Wi-Fi 6 模块留到下一版硬件。
5. **初期不接 Intan 硬件**：用 DDR 回放 `rat128_raw.npy` / `ob48_lfp.npy` 做数字孪生验证，SPI 接口留到 Phase 4 有真实 headstage 再接。
6. **总工期估 6~9 周**（单人、课余时间），分 5 个阶段，每阶段有硬验收标准。

## 2. 目标架构（板级映射）

```
[Phase 4 真实硬件: Intan RHD2164 ×2 SPI]──┐
                                          ├→ 帧缓冲/通道重排 (BRAM)
[Phase 1~3: DDR 回放 rat128 测试向量]─────┘        │ 一帧 128ch, 33µs
                                                   ↓ 按树拓扑序输出
                 T1 预测器（128×16bit 减法器, 父通道值查 BRAM）
                                                   ↓ 残差 (int16)
                 [二期可选: NEAR 阈值量化, 可旁路]
                                                   ↓
                 drice 编码器（k 块自适应 + Rice 编码 + 位打包）
                                                   ↓ ≈31.5 Mbps (61.44/1.949)
                 AXI-Stream → AXI DMA → PS DDR 环形缓冲
                                                   ↓
                 PS（双核 A9）: UDP 千兆网发送 / SD 卡落盘 / 参数下发 / CR 统计
                                                   ↓
                 PC 端: Python 解码器逐位比对 + 实时 CR 显示（验收关口）
```

### 关键设计点（来自实测教训）

1. **帧缓冲 + 拓扑序输出（必有）**：RHD2164 SPI 按固定通道序串行输出，而 T1 树要求父通道先于子通道解码。两者序不一致 → 必须缓存整帧（128×16bit = 4KB，一片 BRAM 搞定）再按拓扑序处理。代价仅 1 帧延迟 33µs。
2. **编码器可单核分时复用**：128ch×30kS/s = 3.84M 样本/s，100MHz 时钟下每样本有 26 个周期——**一个共享 drice 编码器就够**，无需 128 份复制。这是 drice 结构相对 FLAC 的决定性优势（FLAC 的 LPC 在 FPGA 上要每通道独立状态）。
3. **树表静态下发**：128 项×7bit 父通道索引，PS 通过 AXI-GPIO/BRAM 接口手术前标定后写入，运行期不变（避免动态更新引入的同步复杂度；真实犬类布线的树和增益预期参照附七：去冗余后 +4% 左右，但重复通道检测仍值得做）。
4. **zstd 行序教训（附七）**：通道重排模块要支持"电极自然序"布局——压缩后的字节流里相邻残差要来自相邻通道，LZ 类才有增益（drice 是逐通道独立，对此不敏感，但保留灵活性零成本）。

## 3. 关键决策表

| 决策点 | 选项 A | 选项 B | 推荐 | 理由 |
|---|---|---|---|---|
| 核心板 | 7020（85K LC, 1GB DDR3, -2 速度级） | 7010（28K LC, 512MB, -1） | **7020** | 压缩核 7010 也够，但 1GB DDR 可存 2.2 分钟原始流回放；J4 扩展口仅 7020 可用；-2 速度级时序余量大 |
| PS 软件 | 裸机（standalone） | PetaLinux | **裸机起步** | UDP 例程（正点原子 PS 例程 39-43）裸机即可；Linux 等 Wi-Fi 模块/文件系统需求出现再上 |

## 4. 分阶段计划（每阶段有验收标准）

### Phase 0：环境与例程热身（约 1 周）
- 装 Vivado + 板卡资料包，跑通 4 个例程：PL 流水灯（确认下载链路）、PS Hello World（确认 JTAG/串口）、**AXI DMA 环路测试**（PS 例程 20）、**以太网 UDP 测试**（PL 例程 32 或 PS 例程 39）。
- 后两个例程直接是本项目的两块积木：DMA 环路改造成"回放注入 + 压缩流回收"，UDP 例程改造成压缩流发送。
- **验收**：DMA 环路例程跑通且能改buffer大小；UDP 例程在 PC 上收到数据。

### Phase 1：黄金模型固化 + 位流规范（约 1~2 周）★ 最关键
- 把 `drice_nl_test.py` + `bench3.py` 重构为**位精确规范**：
  - 帧格式定义：`sync(32bit) | tree_ver(8) | frame_cnt(32) | NEAR(4) | payload | CRC`
  - drice 的 **k 估计算法逐位定义**：块大小（如 64 样本/通道）、|残差| 求和、k = ceil(log2(sum/N)) 的**整数舍入规则**（Python 整数除法 vs RTL 移位，必须写成伪代码级精度）；
  - Zigzag 映射规则（负数→奇数）；
  - T1 树表二进制格式（128×7bit 父索引 + 每脑区根通道标记）。
- 输出：`golden_encode.py`（输入 npy → 输出标准位流）+ `golden_decode.py` + 互逆校验（rat128 和 ob48 两个数据集全量通过）。
- 生成固定测试向量：每数据集取 10s 段，存 `tv_*.bin` 供 RTL 仿真逐位比对。
- **验收**：编解码互逆 100%；位流文件可在两数据集上复现实测 CR（宽带 ~2.3× / 清醒 LFP ~1.9×）。

### Phase 2：PL 核心 RTL + 仿真对拍（约 2~3 周）
- 模块清单（自底向上）：
  1. `drice_enc.v`——单通道 Rice 编码 + k 自适应（先做）
  2. `bitpacker.v`——跨通道位拼接（可变长 → 字节流）
  3. `t1_predictor.v`——减法器 + 父值缓存（双端口 RAM 存当前帧父通道值）
  4. `frame_buffer.v`——4KB BRAM 帧缓存 + 拓扑序读出
  5. `framer.v`——帧头/同步字/CRC 封装
  6. `axi_stream_top.v`——顶层，AXI-Stream 主接口
- 仿真策略：Vivado XSim（或 cocotb，Python 写测试激励直接对比 golden 位流）；每个模块先单元测试，再顶层联测。
- **验收（硬标准）**：测试向量激励下，RTL 输出位流与 `golden_encode.py` 输出**逐位一致**，两个数据集各 10s；时序收敛 100MHz。

### Phase 3：上板回放验证（约 1~2 周）
- 数据通路：`rat128_raw.npy` → PC 转 bin → SD/以太网加载到 DDR → DMA 按实时速率（61.44Mbps）注入 PL → 压缩 → DMA 回收 → UDP 发出。
- PS 裸机程序：双核分工（core0 收发+统计，core1 参数管理）或单核轮询起步。
- PC 端：Python 接收器 + golden_decode 实时解码 + CR/丢包率显示。
- **验收**：连续 60s 无丢帧回放，PC 端解码数据与源数据逐位一致，实测 CR 与 Python 基准一致；用 `ob48_lfp`（不同树）换树表重跑，验证树表下发通路。

### Phase 4：真实 Intan 接入（约 1~2 周，视硬件到位时间）
- RHD2164 ×2 SPI 主控 RTL（SCLK ≥30MHz 才够 128ch@30kS/s；RHD2164 支持 daisy-chain 或双独立总线，确认手上 headstage 拓扑后定）。
- 板上走 J1/J2 40pin 扩展口接转接板；信号完整性：SCLK 走线短、等长，必要时降 20MHz（带宽仍够：61.44Mbps÷2 = 双总线各 30.72Mbps）。
- 时钟方案：PL 50MHz 晶振 → PLL 倍频出 SPI 时钟与 100MHz 系统时钟；采样触发与帧计数对齐。
- **验收**：真实 Intan 数据实时压缩 + PC 解码一致；示波器确认 SPI 时序余量。

### Phase 5（二期可选）：近无损模式 + hub 层 FLAC
- NEAR 量化器（比较+截断，一个周期）插入 T1 与 drice 之间，验证误差上界 ≤ NEAR×树深（犬类真实布线树深需实测后写入文档，参考 001539 的链深 11 → NEAR=2 worst 20µV）。
- FLAC 立体声在 PS A9 跑 libFLAC（若演示需要）：LFP 1.5kHz 流码率小可行；30kS/s 宽带 128ch 在 A9 上软件编码吞吐不足，**植入端宽带必须靠 PL 的 drice**——这正是管线分层的依据。
- Wi-Fi 6 模块（如 M.2/USB 接口模组）接入评估。

| 板上千兆网 | 1000 Mbps ≫ 31.5 Mbps | 模拟 Wi-Fi 6 链路无压力 |

## 6. 风险与坑（按优先级）

1. **k 估计舍入规则不一致（最高风险）**：Python `/` 与 RTL 除法/移位舍入差 1 个 k，整块位流错位。Phase 1 必须写成"移位+条件加"的整数伪代码，两边照抄。
2. **位流重同步**：无线丢包后解码器靠帧头 sync 字 + CRC 重锁；帧封装格式现在定死，避免二期返工。
3. **SPI 时序与线缆**：RHD2164 SCLK 上限与线缆长度是 Phase 4 的实际约束；先用回放模式把压缩核做扎实，硬件问题后置。
4. **教程例程版本锁定**：领航者例程基于 Vivado 2018.3，换新版本需重新导入 IP（PLL/FIFO 等），第一次别给自己加变量。
5. **J4 扩展口仅 7020 可用**（Bank 13）：若用 7010，Intan 转接板只能走 J1/J2（72 个 IO 足够，但要提前规划引脚）。
6. **FLAC 不要上植入端**：A9 软件编码宽带流吞吐不够，FLAC 只属于 hub/PC 层——这已在实测与架构上双重确认。
